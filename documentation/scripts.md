# Scripts Reference

This document describes every automation script in the repository: what it does, why it was created, and which project phase introduced or last changed it. Phase specs live under [`specs/`](../specs) and the corresponding write-ups live under [`implementation-reports/`](../implementation-reports).

| Script | Purpose | Created | Phase |
|---|---|---|---|
| [`gradlew`](../gradlew) | Standard Gradle wrapper for Linux/macOS/WSL. Runs `clean build`, `test`, and registry CLI tasks without requiring a local Gradle install. | Generated by Gradle at repository scaffolding time. | Phase 0.1 (initial repo baseline) |

## Phase runtime lifecycle — `ops/scripts/`

These scripts start, stop, and observe the local three-node Pub/Sub topology together with the Cardano devnet.

The Pub/Sub containers all listen on the same internal ports (`7000` for peer transport and `8000` for the control API). Docker Compose maps those to distinct localhost ports (`7001..7003` and `8001..8003`) so all three nodes can be reached from the host at the same time.

| Script | Purpose | Created | Phase |
|---|---|---|---|
| [`phase-0.1-up.sh`](../ops/scripts/phase-0.1-up.sh) | Builds the Java application, starts the Cardano devnet, waits for it to become healthy, funds the phase identities, then starts the three Pub/Sub nodes. | Written to satisfy the "Run Phase 0.1 Locally" requirement in `specs/phase-0.1.md`. | Phase 0.1 |
| [`phase-0.1-down.sh`](../ops/scripts/phase-0.1-down.sh) | Tears down the three Pub/Sub node containers and the Cardano devnet. | Companion to `phase-0.1-up.sh`. | Phase 0.1 |
| [`phase-0.1-logs.sh`](../ops/scripts/phase-0.1-logs.sh) | Streams live Docker Compose logs from all three Pub/Sub nodes for local debugging. | Companion to `phase-0.1-up.sh`. | Phase 0.1 |

## Cardano devnet infrastructure — `ops/infra/devnet/`

Introduced in Phase 0.1 to stand up a local Cardano network (`cardano-testnet`) for the Pub/Sub nodes to run against.

| Script | Purpose | Created | Phase |
|---|---|---|---|
| [`scripts/common.sh`](../ops/infra/devnet/scripts/common.sh) | Shared library used by every other devnet script: Docker Compose wrappers, path helpers, `cardano-cli` bindings, identity-creation helpers, funding checks, chain-tip queries, and JSON parsing helpers. | Original devnet baseline per `specs/phase-0.1.md`. | Phase 0.1, extended in Phase 0.2.1 to support Cardano-backed registry operations |
| [`scripts/init.sh`](../ops/infra/devnet/scripts/init.sh) | Generates Cardano payment keys/addresses for `registry-deployer`, `node-1`, `node-2`, and `node-3` if they don't already exist. | Original devnet baseline. | Phase 0.1 |
| [`scripts/start.sh`](../ops/infra/devnet/scripts/start.sh) | Starts the devnet, either by running `cardano-testnet` directly (if on `PATH`) or via Docker Compose with pinned tool versions; writes runtime network config to `runtime/network.env`. | Original devnet baseline. | Phase 0.1 |
| [`scripts/status.sh`](../ops/infra/devnet/scripts/status.sh) | Queries and prints the current Cardano chain tip as JSON, used to confirm the devnet is live. | Original devnet baseline. | Phase 0.1 |
| [`scripts/wait-healthy.sh`](../ops/infra/devnet/scripts/wait-healthy.sh) | Polls chain-tip advancement (up to 120 attempts, 2s apart) and fails if blocks stop advancing, used as a readiness gate before funding/starting nodes. | Original devnet baseline. | Phase 0.1 |
| [`scripts/stop.sh`](../ops/infra/devnet/scripts/stop.sh) | Stops any local `cardano-testnet` process and brings the Docker Compose devnet down. | Original devnet baseline. | Phase 0.1 |
| [`scripts/reset.sh`](../ops/infra/devnet/scripts/reset.sh) | Full devnet reset: stop, remove volumes, clear local state/keys/runtime directories, then reinitialize from scratch. Used by acceptance runs to guarantee a clean starting state. | Original devnet baseline. | Phase 0.1 |
| [`scripts/fund-identities.sh`](../ops/infra/devnet/scripts/fund-identities.sh) | Funds the four phase identities from a generated testnet UTxO source: builds and submits real funding transactions, then verifies balances/UTxO counts meet the minimum requirements, failing rather than assuming phantom funds. | Original stub in Phase 0.1; rewritten in Phase 0.1.1 to perform real identity generation and funding; hardened further in Phase 0.1.2 per `specs/phase-0.1.2.md` ("Update `fund-identities.sh`"). | Phase 0.1, Phase 0.1.1, Phase 0.1.2 |
| [`container/start-testnet.sh`](../ops/infra/devnet/container/start-testnet.sh) | Docker container entrypoint that launches `cardano-testnet` with configurable network magic, pool node count, slot/epoch lengths, active-slots coefficient, and output directory. | Original devnet baseline. | Phase 0.1 |

## Topic Registry operations — `scripts/registry/`

Introduced in Phase 0.2 to give operators/tests a CLI surface over the on-chain Topic Registry, per the file list in `specs/phase-0.2.md`.

| Script | Purpose | Created | Phase |
|---|---|---|---|
| [`common.sh`](../scripts/registry/common.sh) | Shared registry library: runtime directory setup, Gradle invocation helpers (with Windows/WSL detection), Node.js helpers, and the `registry_cli()` wrapper that invokes the Java `registry-cardano` CLI with a timeout and platform-specific path handling. | Added while hardening the registry scripts against the real Cardano ledger. | Phase 0.2.1 |
| [`build.sh`](../scripts/registry/build.sh) | Downloads Aiken (if not already cached), runs `aiken check` on the `topic-registry` contract, and generates the Plutus script artifacts (`plutus.json`). | Listed in `specs/phase-0.2.md` as a required registry entry point. | Phase 0.2, updated in Phase 0.2.1 |
| [`build-aiken-wsl.sh`](../scripts/registry/build-aiken-wsl.sh) | WSL-specific wrapper for building the Aiken contract on Windows systems where Aiken must run inside WSL/Cygwin bash; downloads and executes Aiken with the correct path translation. | Added to unblock Windows-based Aiken builds. | Phase 0.2.1 |
| [`deploy.sh`](../scripts/registry/deploy.sh) | Deploys the Topic Registry validator/minting policy to Cardano via the registry CLI's `deploy` command; writes `TOPIC_REGISTRY_VALIDATOR_ADDRESS` and `TOPIC_POLICY_ID` to `deployment.env`. | Listed in `specs/phase-0.2.md` as a required registry entry point. | Phase 0.2, updated in Phase 0.2.1 |
| [`create-topic.sh`](../scripts/registry/create-topic.sh) | Creates a new topic on-chain. Usage: `create-topic.sh <signer> <name> <admins> <publishers> <replication_factor> <retention_period>`. | Listed in `specs/phase-0.2.md` as a required registry entry point. | Phase 0.2 |
| [`delete-topic.sh`](../scripts/registry/delete-topic.sh) | Deletes a topic (marks it as an inactive tombstone rather than removing it). Usage: `delete-topic.sh <signer> <topicId>`. | Listed in `specs/phase-0.2.md` as a required registry entry point. | Phase 0.2 |
| [`add-owner.sh`](../scripts/registry/add-owner.sh) | Adds an owner to a topic (owner-only mutation). Usage: `add-owner.sh <signer> <topicId> <owner>`. | Listed in `specs/phase-0.2.md` as a required registry entry point. | Phase 0.2 |
| [`remove-owner.sh`](../scripts/registry/remove-owner.sh) | Removes an owner from a topic (owner-only mutation, blocked if it would leave zero owners). Usage: `remove-owner.sh <signer> <topicId> <owner>`. | Listed in `specs/phase-0.2.md` as a required registry entry point. | Phase 0.2 |
| [`direct-last-owner-removal.sh`](../scripts/registry/direct-last-owner-removal.sh) | Constructs a direct Cardano transaction that attempts to remove the last owner via a zero-owner output datum, bypassing the Java API's own safety check. Used only to prove the Aiken validator itself rejects the invariant violation. | Added as negative-path test tooling for the on-chain validator. | Phase 0.2.1 |
| [`add-admin.sh`](../scripts/registry/add-admin.sh) | Adds an admin to a topic (owner-or-admin mutation). Usage: `add-admin.sh <signer> <topicId> <admin>`. | Listed in `specs/phase-0.2.md` as a required registry entry point. | Phase 0.2 |
| [`remove-admin.sh`](../scripts/registry/remove-admin.sh) | Removes an admin from a topic (owner-or-admin mutation). Usage: `remove-admin.sh <signer> <topicId> <admin>`. | Listed in `specs/phase-0.2.md` as a required registry entry point. | Phase 0.2 |
| [`add-publisher.sh`](../scripts/registry/add-publisher.sh) | Adds a publisher to a topic (owner-or-admin mutation). Usage: `add-publisher.sh <signer> <topicId> <publisher>`, or `add-publisher.sh --node <signer> <topicId> <node>` to register that node's Ed25519 event publisher key ID. | Listed in `specs/phase-0.2.md` as a required registry entry point. | Phase 0.2, updated in Phase 0.3 |
| [`remove-publisher.sh`](../scripts/registry/remove-publisher.sh) | Removes a publisher from a topic (owner-or-admin mutation). Usage: `remove-publisher.sh <signer> <topicId> <publisher>`. | Listed in `specs/phase-0.2.md` as a required registry entry point. | Phase 0.2 |
| [`set-replication-factor.sh`](../scripts/registry/set-replication-factor.sh) | Sets a topic's replication factor (owner-or-admin mutation, must stay positive). Usage: `set-replication-factor.sh <signer> <topicId> <replication_factor>`. | Listed in `specs/phase-0.2.md` as a required registry entry point. | Phase 0.2 |
| [`set-retention-period.sh`](../scripts/registry/set-retention-period.sh) | Sets a topic's retention period (owner-or-admin mutation, must stay positive). Usage: `set-retention-period.sh <signer> <topicId> <retention_period>`. | Listed in `specs/phase-0.2.md` as a required registry entry point. | Phase 0.2 |
| [`query.sh`](../scripts/registry/query.sh) | Queries registry state. Supports `--utxos` (list registry UTxOs), `--all` (all topics), `--topic <topicId>` (one topic), or a default summary view. | Listed in `specs/phase-0.2.md` as a required registry entry point. | Phase 0.2, updated in Phase 0.2.1 |
| [`export-aiken-scripts.mjs`](../scripts/registry/export-aiken-scripts.mjs) | Node.js utility that extracts compiled Aiken validator scripts from the `plutus.json` blueprint and writes them out as individual `PlutusScriptV3` JSON files under `contracts/topic-registry/build/cardano-cli/` for use by `cardano-cli`. | Added to bridge Aiken's build output to the Cardano CLI's expected script format. | Phase 0.2, updated in Phase 0.2.1 |

## Event operations — `scripts/events/`

Introduced in Phase 0.3 to publish and inject signed event envelopes through a node's localhost control API.

| Script | Purpose | Created | Phase |
|---|---|---|---|
| [`publish.sh`](../scripts/events/publish.sh) | Publishes an event through `POST /v1/events/publish`. Supports plain-text or base64 payloads, plus acceptance-only `--force-broadcast` and `--tamper-signature` flags for receiver-side validation tests. | Written for the Phase 0.3 node control API and negative-path acceptance requirements. | Phase 0.3 |
| [`inject.sh`](../scripts/events/inject.sh) | Re-broadcasts a previously captured event envelope through `POST /v1/events/inject`, used by acceptance to prove duplicate suppression against the exact same event ID. | Written for the Phase 0.3 duplicate suppression acceptance check. | Phase 0.3 |
| [`publisher-key-id.sh`](../scripts/events/publisher-key-id.sh) | Reads a running node's Ed25519 event publisher key ID from `GET /v1/events/publisher-key-id`, used when registering node publishers in the Cardano Topic Registry. | Written for the Phase 0.3 publisher identity decision. | Phase 0.3 |

## Aiken smart contracts — `contracts/topic-registry/`

Not shell scripts, but the on-chain logic that the registry scripts above build, deploy, and drive:

| File | Purpose | Phase |
|---|---|---|
| [`validators/topic_registry.ak`](../contracts/topic-registry/validators/topic_registry.ak) | Aiken validators for the Topic Registry: `topic_policy` (mints exactly one unique topic token from a consumed creation UTxO) and `topic_state` (enforces the owner/admin authorization matrix, positive replication/retention values, non-empty owner sets, irreversible deletion, and token preservation across state transitions). | Phase 0.2.1 |
